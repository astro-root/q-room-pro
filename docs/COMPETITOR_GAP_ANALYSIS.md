# 競合機能との差分と実装方針

競合調査: [Q-ROOM-PRO_COMPETITOR_ANALYSIS.md](./Q-ROOM-PRO_COMPETITOR_ANALYSIS.md)

## 現在の実装

| 領域 | 実装状況 | 評価 |
|---|---|---|
| ルーム作成・コード参加 | HTTP API、ホスト/参加者トークン | 実装済み |
| 基本ルール | 7○3×、10by10 | 2ルールに限定 |
| 早押し | 大型タッチUI、サーバー側で順序確定、Web Spaceキー、ネイティブ/ブラウザー触覚 | コア体験はある。効果音・実測低遅延は未対応 |
| 判定・スコア | ○/×、正解数と得点、勝敗表示 | 手動スコア修正なし |
| 誤判定の復旧 | 直前の司会判定を1回Undo | 今回追加 |
| 司会の素早い操作 | PCキーボードで1=正解、2=不正解、N=次問、U=Undo | 今回追加 |
| 同期・復旧 | SSE、切断後のHTTP再取得と再接続 | イベント履歴、永続化なし |
| モバイル | レスポンシブUI、PWAシェル、Capacitor、safe area、触覚 | 実機での遅延・スリープ抑制評価は未実施 |
| 追加競技形式 | チーム、観戦、ボード回答、Delay、休みルール | 未実装 |
| 運営補助 | チャット、リアクション、録画、自動進行、AI判定 | 未実装。コア価値検証後に再評価 |

## 優先順位

### S: 競技の信頼性と入力体験

- 直前の判定を安全にUndoする（実装済み。現状は直前1件のみ）
- ゲーム遷移、得点境界、タイマー境界の自動検証を整備する
- 早押しのローカル即時フィードバックとサーバー確定を分け、入力から同期までを計測する
- 効果音と通信状態の表示、実機の画面スリープ抑制を検討する

### A: 司会運営とルール拡張

- 誤答後の受付、休み、プレイヤー別Delayなどをルール設定としてモデル化する
- 司会者のスコア修正と複数段階の操作履歴を、監査可能な形で追加する
- ルール定義をドメイン層に集約し、UIがルール固有条件を持たないようにする
- 永続ストアとイベント履歴を導入し、再起動後のルーム復旧を可能にする

### B: 利用シーンの拡大

- チーム戦と観戦を、権限・状態モデルを含めて設計する
- ボード回答や問題メディアは、基本進行と入力品質を確認してから追加する
- オフライン/ローカル通信は大会会場での需要を確認して設計する

### C: 競合の機能数を追う機能

- チャット、Discord連携、CPU、AI判定、自動進行、録画、音声通話は、コアUXの改善が測れるまでは後回しにする

## アーキテクチャ上の注意

- サーバーをゲーム状態の唯一の確定元にする。スコアや判定をクライアントから直接書き換えない。
- ルールを `src/domain.js` の状態遷移として定義し、サーバーの認可・タイマーとUIを分ける。
- Undoは競技操作の履歴とバージョン管理を一緒に扱う。並行操作や再送で過去状態を上書きしない。
- SSEは現在スナップショットを配信する。再接続を強くするには永続イベントIDと履歴再生が別途必要。

## 次の実装候補

Undoの複数履歴化より先に、ドメイン遷移の自動検証と早押し入力の遅延計測を行う。結果に基づいて、効果音・スリープ抑制・追加ルールの順を決める。
