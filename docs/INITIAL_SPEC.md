# Q-Room Pro 開発プロジェクト

あなたは、このプロジェクトの**シニアソフトウェアエンジニア、UI/UXデザイナー、プロダクトアーキテクト**として開発を担当してください。

これからGitHub上の新しいリポジトリで、競技クイズ向けサービス「Q-Room Pro」をゼロから開発します。

このリポジトリは完全な新規プロジェクトです。

既存のQ-Roomなどのコードを移植したり、既存リポジトリを前提にした設計をしたりせず、**Q-Room Proそのものをゼロから設計してください。**

---

# 1. プロダクト概要

サービス名：

**Q-Room Pro**

競技クイズの例会・練習・大会などで利用できる、

**「早押し・ゲーム進行・スコア管理を一体化したクイズルームサービス」**

を作ります。

最大の特徴は、

> **Webサービスでありながら、スマートフォンではネイティブアプリとして利用でき、スマートフォンを競技クイズ専用端末のように使えること**

です。

単なるWeb版の早押しボタンではありません。

PCでは運営・問題表示・スコアボードなどを快適に操作でき、スマートフォンではプレイヤーが極めて高速かつ直感的に早押しできることを目指します。

---

# 2. 対応プラットフォーム

最終的に以下をサポートします。

* Web
* iOS
* Android

ただし、

**すべてを無理に同じUI・同じ実装にする必要はありません。**

共通化できるものは共通化しつつ、

* WebはPC・タブレット・スマートフォン
* iOSはiPhone
* AndroidはAndroidスマートフォン

それぞれに適したUXを実装してください。

特にプレイヤーの早押し画面については、スマートフォンでの操作性を最優先してください。

---

# 3. プロダクト思想

Q-Room Proでは、

> **「スマホを早押しボタンにする」**

ことだけを目的にしません。

最終的には、

> **「競技クイズのゲームルームを、スマートフォンやPCだけで簡単に作成・運営できる」**

ことを目指します。

例えば、

```text
Q-Room Pro

ゲームルーム
├── プレイヤー
├── 司会
├── 問題
├── 早押し
├── 正誤判定
├── スコア
├── ゲームルール
└── リザルト
```

というゲーム全体を管理できるサービスにします。

---

# 4. 最重要UX

このプロジェクトで最も重要なのは、

**早押しボタンの操作感**

です。

通常のWebボタンのような、

「クリック → 少し遅れて表示が変わる」

という体験にはしないでください。

理想は、

```text
指が画面に触れる
↓
即座に押下を認識
↓
Haptic Feedback
↓
効果音
↓
ボタン状態変更
↓
早押し結果をゲームへ送信
```

という体験です。

可能な限り低レイテンシで実装してください。

ただし、

**「通信を含めて完全に0ms」「絶対に公平」など、技術的に保証できないことを仕様として約束してはいけません。**

OS・端末・ネットワークの制約を考慮し、保証できる範囲と保証できない範囲を明確にしてください。

---

# 5. 早押しの公平性

これは本プロジェクトの重要な技術課題です。

複数プレイヤーがほぼ同時に押した場合、

```text
Player A
Player B
Player C
```

の誰が最初だったかを判定する必要があります。

しかし、

```text
端末A → サーバー
端末B → サーバー
端末C → サーバー
```

ではネットワーク遅延が存在します。

したがって、

**サーバーに到着した順番 = 実際に押した順番**

とは限りません。

この問題について、

* クライアントタイムスタンプ
* サーバータイムスタンプ
* サーバー時刻との同期
* RTT
* WebSocket
* Firebase
* WebRTC
* ローカルネットワーク
* Bluetooth
* Wi-Fi Direct

などを比較してください。

そして、

**現実的にどこまで公平性を担保できるか**

を設計段階で明確にしてください。

# 6. MVP

最初から巨大なサービスを作らないでください。

MVPの目的は、

> **「Q-Room Proのコアとなる競技クイズ体験を実際に使える状態にする」**

ことです。

MVPでは以下を中心にします。

## プレイヤー

* プレイヤー名
* プレイヤー参加
* 大型早押しボタン
* 早押し状態
* 正解 / 不正解状態
* 得点
* ○数
* ×数
* ペナルティ状態

## 司会

* ゲーム開始
* 問題開始
* 問題終了
* 早押し結果確認
* 正解 / 不正解判定
* 次の問題
* プレイヤー状態確認

## ルール

最低限、

* 7○3×
* 10by10

を検討してください。

ただし、これらのルールをUIに直接埋め込まないでください。

ゲームルールを独立したドメインロジックとして設計し、将来的にルールを追加できる構造にしてください。

## リザルト

* 順位
* 得点
* ○
* ×
* ゲーム結果

# 8. 画面構成

最低限、以下を検討してください。

## ホーム

* 新しいルームを作成
* ルームに参加
* 最近のゲーム
* 設定

## ルーム作成

* ルーム名
* ゲームルール
* プレイヤー設定
* ゲーム設定

## ロビー

* ルームID
* 参加者一覧
* 準備状態
* ゲーム開始

## プレイヤー画面

最重要画面。

画面を極力シンプルにしてください。

必要な情報だけを表示します。

例えば、

```text
┌─────────────────┐
│ Root       5○ 1× │
│                 │
│                 │
│                 │
│    BUZZ         │
│                 │
│                 │
│   500 points    │
└─────────────────┘
```

のような方向性です。

ただし、これは例なので、そのまま採用する必要はありません。

## 司会画面

* 問題番号
* タイマー
* 問題状態
* 押したプレイヤー
* 正解 / 不正解
* プレイヤー一覧
* スコア
* 次の問題

## スコアボード

PCやタブレットでも見やすい大型表示を想定します。

# 9. UI/UX原則

以下を重視してください。

### プレイヤー画面

* 大きなタップ領域
* 親指で押しやすい
* 誤タップしにくい
* 片手操作を考慮
* 縦画面を基本
* 不要なUIを排除
* フルスクリーンを活用
* 視認性を高くする
* 暗い会場でも見やすくする
* 明るい会場でも見やすくする

### 競技中

プレイヤーが、

「今押せるのか？」

「誰が押したのか？」

「自分は正解したのか？」

「今何点なのか？」

を一瞬で理解できる必要があります。

# 11. アーキテクチャ

以下の責務を可能な限り分離してください。

```text
UI
↓
Application
↓
Domain
↓
Infrastructure
```

特に、

* ゲーム状態
* スコア計算
* ルール判定
* 早押し判定
* 通信

をUIから分離してください。

将来的にWeb / iOS / AndroidでUIを変えても、ゲームロジックを再利用できる構造を目指してください。

```text

↓

↓

↓

↓
```

のような状態遷移を検討してください。

不正な状態遷移が発生しないようにしてください。

# 14. オフライン

# 20. 開発上の重要ルール

以下を厳守してください。

### ルール1

**過剰設計しない。**

MVPに必要ない機能を勝手に実装しない。

### ルール2

**技術的に不可能・保証できないことは明確に指摘する。**

### ルール3

**既存サービスをそのままコピーしない。**

競技クイズに必要なUXを分析し、Q-Room Pro独自の設計を考える。

### ルール4

**UIよりゲームロジックを優先して正しく設計する。**

### ルール5

**ゲーム状態を一貫して管理する。**

### ルール6

**プラットフォーム固有機能を無理に共通化しない。**

特にHaptic、音声、バックグラウンド、通信などは各OSの特性を尊重する。

### ルール7

**コードを書く前に設計上の重大な問題を指摘する。**

### ルール8

**実装するときは、小さな単位で実装してテストする。**

一度に巨大な変更を行わない。

# 21. 最終的な目標

最終的にQ-Room Proを、

> **「競技クイズをするなら、とりあえずこれを開けばいい」**

と言われるサービスにしてください。

PCでは運営しやすく、

スマートフォンでは早押しが気持ちよく、

ゲーム状態とスコアは正確に管理され、

ネットワーク環境が多少悪くても可能な限り安定して動作する。

そのために、単なる機能数ではなく、

**競技クイズにおける操作速度・視認性・信頼性・ゲーム進行の快適さ**

を最優先してください。
