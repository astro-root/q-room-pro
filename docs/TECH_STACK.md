# 技術選定

## 比較

| 案 | Web | iOS/Android | 触覚・音 | 実機レスポンス | MVP速度 | 判断 |
|---|---|---|---|---|---|---|
| Flutter | 対応 | 強い | ネイティブAPI利用可 | 高い | 中 | モバイル優先なら候補。Web運営画面とのUI共用は利点が薄い |
| React Native | Webは追加構成 | 強い | ネイティブモジュール | 高い | 中 | 3画面を一貫したWeb基盤にしにくい |
| React + PWA | 強い | インストール可能 | Web APIに制約 | ブラウザー依存 | 高い | まずWeb MVPに適する。iOSのPWA制約は残る |
| React + Capacitor | 強い | ストア配布可能 | プラグインで対応 | WebView依存 | 高い | Web共有を保った後続ネイティブ化に適する |
| KMP + SwiftUI/Compose | Webは別実装 | 強い | OS固有実装 | 高い | 低い | MVPの速度・Web共有に不利 |

## 推奨
段階導入を採用する。現在のMVPは依存のないES Modules、HTML、CSSとNode.js標準HTTP APIで構成し、ゲームドメインをUIから独立させる。リアルタイム配信にはSSE、操作にはHTTP POSTを用いる。利用規模や双方向通信要件が確認できた段階でWebSocketを評価する。製品化のWeb UIにはReact/PWA、モバイルで触覚・音・配布要件が明確になった段階でCapacitorを評価する。全プラットフォームで同じ入力性能や機能を保証しない。

## 技術上の約束
- 早押しでは入力端末のローカル表示を直ちに変える。
- `navigator.vibrate`は対応ブラウザーに限って短く利用する。
- サーバーがゲーム状態を確定し、クライアントは表示・入力・触覚を担当する。現在はHTTP/SSEを使う。
- ブラウザーのクライアント時刻は端末ごとにずれるため、単独で勝敗の決定根拠にしない。
